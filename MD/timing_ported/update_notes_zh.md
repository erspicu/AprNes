# AprNes 更新說明 — TriCNES Timing 架構移植與效能優化

## 為什麼需要這次更新

之前的 AprNes 已通過 AccuracyCoin（Commit 62ed684）136/136 以及 blargg 等測試 174/174，當時我認為模擬精度已經相當完善。然而，在實際執行 scanline-a1 和 colorwin_ntsc 等測試 ROM 時，發現了比較明顯的畫面瑕疵。經過深入追查，確認根本原因是 PPU 模擬的 timing 顆粒度不夠精確，仍然存在實際的時序問題。

## TriCNES 與移植過程

在解決這些問題的過程中，我最終決定提升 timing 的模擬精度，並採用了 TriCNES 所設計的 timing 架構，移植了其中部分關鍵做法。

TriCNES 是一款非常優秀的 NES 模擬器。它的設計方向比較偏向作者個人興趣下的學術研究，以及追求 TAS（Tool-Assisted Speedrun）執行過程的極致正確性，並非以一般用戶的使用體驗為優先考量。從目前的發展趨勢來看，TriCNES 的設計方向一直在朝真實電路級行為邁進，這點令人印象深刻。

### 第一次移植：改善 PPU 測試 ROM

在移植 TriCNES 之前，AprNes 的 AccuracyCoin（Commit 62ed684）成績就已經達到 136/136。第一次移植 TriCNES 的結構，主要目的是解決其它 PPU 測試 ROM（如 scanline-a1、colorwin_ntsc 等）中存在的畫面瑕疵問題。這次移植提升了整體 timing 精度，blargg 測試也從 174 增加到 184 項全數通過（包含新增的 10 個 PAL APU 測試）。

### AccuracyCoin 新版更新的衝擊

AccuracyCoin 後來更新到了新版本（Commit 03385dd），測試項目從 136 增加到 138 項。在這個新版測試下，之前版本的 AprNes 被擊敗了 10 個項目，成績掉到 128/138。

### 第二次移植：應對新版 AccuracyCoin

為了應對 AccuracyCoin（Commit 03385dd）的新挑戰，我又進行了一輪 timing 架構移植。AprNes 的成績回升到 135/138，經過進一步修復達到 137/138，但有一個測試項目（$2007 Stress Test）無論如何都難以光靠行為層級的模擬方式解決。

最後，我進一步從 TriCNES 更新版本中移植了 SR Latch Pipeline 設計。TriCNES 更新版的架構中包含了更多基於真實電路描述（RTL）的設計理念，例如用 5 階段 NOR gate 鏈來模擬 $2007 讀寫的時序管線，令人嘆為觀止。

我沒有全部採用這些電路級設計，僅選擇性地移植了解決最後一個測試問題所需的相關部分。最終達到 **138/138** 的 AccuracyCoin（Commit 03385dd）滿分成績，以及 **184/184** 的 blargg 測試全通過。

## 效能影響與優化

### 效能衝擊

移植 TriCNES 的 timing 架構後，整體運作效能受到了相當大的影響。真實電路級的時序模擬（如 SR Latch 每個 PPU dot 都需要推進狀態、Master Clock 驅動的子週期精確排程等）帶來了不可忽視的運算成本。

### Catchup 優化的困難

傳統的模擬器加速技巧 — Catchup（延遲執行，需要時再批次補跑）— 在這個架構下變得極難實現。原因是：

- NMI/IRQ 的觸發精確到 Master Clock 層級
- SR Latch pipeline 每個 dot 都必須推進
- APU 的 GET/PUT 半周期交替影響 DMC DMA 時序
- AccuracyCoin（Commit 03385dd）的測試直接驗證這些微觀行為

目前已完成的安全優化包括：位元管線化（bitwise SR latch）、SWAR 64-bit 批次操作、managed array 消除、方法 inline、以及 Mode 0 音效取樣的 catchup。但我相信仍然存在更多的優化空間，只是需要更多時間。

### 關於效能的現實考量

理論上，以現代 CPU 的效能來說，只要不是在 CPU 上跑 Visual6502 那種 Gate-level Netlist 層級的模擬，效能實際上都不是問題。問題在於 AprNes 為了不浪費現代 CPU 的能力，加入了不少影音處理的 DSP 鏈（NTSC 類比模擬、CRT 效果、音效後處理等），而在模擬器核心的處理成本因為高精度 timing 模型大幅增加的情況下，DSP 鏈的開銷就變得格外可觀。

目前已經優化到基礎模式可以流暢運行，但開啟類比模式（特別是 Ultra Analog + CRT 模擬）時，處理性能可能會變得吃力。

## Benchmark 工具

這一版更新附帶了幾個 Benchmark 批次檔，可以用來評估你的電腦上的運行效能：

- **benchmark_baseline.bat** — 基準測試。純數位模式（1x 解析度、無濾鏡、無類比處理），測量模擬器核心的純粹效能。採用 JIT 暖機 → 冷卻 → 兩次有效測量的協議，取最佳成績。
- **benchmark_full.bat** — 完整管線測試。開啟 NTSC + 音效 Mode 2（Modern Stereo）+ Analog + Ultra Analog + CRT，以 2x/4x/6x/8x 四種解析度分別測試，全面評估影音處理管線在不同負載下的效能表現。
- **benchmark_analog_full.bat** — 極限壓力測試。以最高負載配置運行：8x 解析度（2048x1920）、Ultra Analog、RF 輸出、CRT 模擬、音效 DSP Mode 2。用於測試你的硬體在最極端場景下的承受能力。

未來可能會獨立成一個 benchmark 測試工具專案。

## 定位與建議

我要特別強調：**AprNes 本身的存在比較偏向概念驗證與個人興趣**。它不是以大眾需求為最終設計方向的程式。我有我自己想測試、研究和實踐的東西。

如果你在意的是：

- 支援多少 Mapper
- 介面完善程度
- 附帶功能（除錯器、金手指、存檔等）

那麼目前最好的選擇仍然是 **Mesen2**。這些面向大眾的功能才是決定一款模擬器「好不好用」的關鍵因素。至於不計代價把模擬正確性推到極致，本質上比較偏向研究或個人挑戰的目的。

**如果你覺得之前的 AprNes 版本用起來比較流暢，也喜歡它在音效和畫面上的處理效果，而你的電腦效能不足以承受新版所需的計算代價，那就沒有必要更新到新版本。**

## 未來發展

- **持續優化** — 希望在不犧牲精度的前提下進一步改善效能
- **增加中文常用 Mapper** — 提升中文遊戲的兼容性
- **最終以 .NET 10 版本發佈** — 類比模式和 CRT 部分很有可能會使用 GPU 加速
- **Visual6502 研究** — 在 AprNes 告一段落後，我計劃轉向研究 Visual6502 專案，設計出一套能讓 Gate-level Netlist 模擬真正以 real-time 方式運行遊戲的方案。**這才是我真正想做的東西。**

## 授權與致謝

AprNes 專案本身不主張任何版權，採用 **WTFPL** 授權。如果我的任何設計是你覺得喜歡的、覺得不足可以改善的、或是希望移植到你自己的專案中的 — 一切都歡迎。

我想推廣的只是一個「概念」。程式本身是借助 AI（透過網路相關資料訓練而成的模型）來協助實現的，因此理論上我真正的產出，只有我對這個專案的設計概念本身。

如果有人欣賞這個概念，歡迎完善它。特別是影音 DSP 鏈的部分，很可能還隱藏著不少學術理論上的錯誤需要修正。
