# 07 PPU Memory and Registers

## What This Chapter Solves

The CPU can't draw pixels directly. The NES picture is generated by the PPU itself, using VRAM, CHR, OAM, palette, and register state. The CPU controls the PPU only indirectly, through the memory-mapped registers `$2000-$2007`.

This chapter covers the PPU memory map, key registers, the scroll latch, and AprNes's implementation.

## NES Hardware Concepts

**A foundational concept first**: the NES PPU **has no framebuffer**. It does not store the entire frame in some memory and then display it. The PPU "**computes as it scans**" — as the electron beam reaches each dot, the PPU pulls from pattern table + name table + attribute + palette + sprite OAM, computes the colour, and emits it on the spot.

**Everyday analogy**: the background isn't "one whole picture," it's a **mosaic collage**:

- **Pattern table** (the sticker library): 256 × 8×8 tile templates — a "sticker book."
- **Name table** (the placement map): 32×30 = 960 cells, each holding a sticker number. Together they form the 256×240 background.
- **Attribute table** (colour-zone map): for each 32×32 region, picks one of 4 palettes.
- **Palette RAM** (32 bytes): the active palettes (NES has 64 universal colours; only 32 are usable per frame).
- **OAM** (sprite table): 64 sprites × 4 bytes = 256 bytes, listing the moving characters on screen.

```
+------------+    +------------+
| Pattern    |    | Name       |     "Take sticker #42 from the pattern
| table      | ←  | table      | →   library and place it in cell (15, 8)"
| (CHR ROM)  |    | (1KB VRAM) |
+------------+    +------------+
                        ↓
                  +------------+    +------------+
                  | Attribute  | →  | Palette    |
                  | table      |    | RAM (32B)  |
                  +------------+    +------------+
                        ↓                ↓
              TV's dot at (255, 127) ⇒ one NES colour (0-63)
```

PPU address space (note this is the PPU's own 14-bit address space, completely separate from the CPU's 16-bit space):

```text
$0000-$0FFF  Pattern table 0  ┐
$1000-$1FFF  Pattern table 1  ┘ usually CHR ROM/RAM from cartridge, 8 KB

$2000-$23FF  Nametable 0      ┐
$2400-$27FF  Nametable 1      │ 4 logical nametables, but the
$2800-$2BFF  Nametable 2      │ console's VRAM is only 2 KB physically
$2C00-$2FFF  Nametable 3      ┘ → must mirror two-by-two

$3000-$3EFF  Nametable mirror

$3F00-$3F0F  Background palette (4 sets × 4 colours)
$3F10-$3F1F  Sprite palette (4 sets × 4 colours)
$3F20-$3FFF  Palette mirror
```

Pattern table holds tile graphics. Each 8×8 tile uses 16 bytes split into low and high bitplanes. **Why two bitplanes?** Each pixel is 2-bit (4 colours). Hardware groups the low bits of 8 pixels in one byte and the high bits in another, so the PPU fetches both in parallel and gets the colour index for 8 pixels at once:

```
tile bytes $00-07: pattern low bitplane     (low bit per pixel for each row)
tile bytes $08-0F: pattern high bitplane    (high bit per pixel for each row)

Example: byte $00 = 01000010, byte $08 = 11000000
   pixel  0 1 2 3 4 5 6 7
   low    0 1 0 0 0 0 1 0
   high   1 1 0 0 0 0 0 0
   merged 2 3 0 0 0 0 1 0  ← 2-bit colour index per pixel
```

The name table stores screen tile indices. **Background is not a bitmap**; it's a sequence of tile indices. One screen = 32 × 30 = 960 bytes specifying which tiles to place.

The attribute table picks a palette per 32×32 pixel region (each attribute byte controls four 16×16 sub-regions, 2 bits each). **This is the source of NES colour limitations** — those classic "color tear" edges around sprites in old games happen when a character crosses an attribute boundary.

Palette RAM maps 2-bit pattern + 2-bit attribute = 4-bit palette index, into one of the NES's 64 colours.

## PPU Registers

The CPU controls the PPU via `$2000-$2007`:

```text
$2000 PPUCTRL
$2001 PPUMASK
$2002 PPUSTATUS
$2003 OAMADDR
$2004 OAMDATA
$2005 PPUSCROLL
$2006 PPUADDR
$2007 PPUDATA
```

### `$2000` PPUCTRL

Controls:

- base nametable.
- VRAM increment is 1 or 32.
- sprite / background pattern table.
- sprite size.
- NMI enable.

### `$2001` PPUMASK

Controls:

- background enable.
- sprite enable.
- left 8-pixel mask.
- greyscale.
- emphasis bits.

### `$2002` PPUSTATUS

On read:

- bit 7: VBlank.
- bit 6: sprite 0 hit.
- bit 5: sprite overflow.

Reading `$2002` also resets the `$2005/$2006` write latch.

### `$2005` and `$2006`

These two registers don't behave like ordinary writes.

`$2005`:

- 1st write: horizontal scroll.
- 2nd write: vertical scroll.

`$2006`:

- 1st write: VRAM address high byte.
- 2nd write: low byte and schedule an update of `v`.

### `$2007`

`$2007` reads / writes PPU memory. Non-palette reads have a read-buffer delay. Each access advances the VRAM address by 1 or 32 according to `$2000` bit 2.

## Beginner-Friendly Simplification

Start by introducing Loopy's scrolling variables:

- `v`: current VRAM address.
- `t`: temporary VRAM address.
- `x`: fine X scroll.
- `w`: write toggle.

Get `$2005/$2006/$2007` approximately right first, then add delays, open bus, and palette-read corner cases.

## AprNes / NesCore Implementation Mapping

Relevant fields in `PPU.cs`:

- `vram_addr`: current VRAM address.
- `vram_addr_internal`: temporary address.
- `FineX`: fine X.
- `vram_latch`: write toggle.
- `ppu_2007_buffer`: PPUDATA read buffer.
- `openbus`: PPU bus residual.

Register handlers:

- `ppu_w_2000()`: PPUCTRL, including the TriCNES-model 2-master-clock push.
- `ppu_w_2001()`: deferred update of rendering enable, mask, emphasis.
- `ppu_r_2002()`: status read with deferred VBlank clear and latch reset.
- `ppu_w_2005()`: schedule scroll update.
- `ppu_w_2006()`: schedule t → v copy.
- `ppu_r_2007()` / `ppu_w_2007()`: pass through the `$2007` SR-latch pipeline.

In `ppu_new.cs`:

- `PpuPhase2_DeferredUpdates()` handles the `$2005/$2006` delay.
- `PPU_DATA_Pipeline_Step1()` and `PPU_DATA_Pipeline_Step3()` handle the `$2007` read/write pipeline.

## Common Mistakes

- Implementing `$2007` reads to return VRAM directly, ignoring the read buffer.
- Failing to reset the `$2005/$2006` latch after reading `$2002`.
- Ignoring palette mirroring, especially the special cases like `$3F10` mirroring `$3F00`.
- Using a simple VRAM read/write model while rendering is enabled.
- Treating `$2005/$2006` writes as instantly updating all internal state, breaking split-scroll timing.

## Chapter Recap

1. The CPU manipulates the graphics chip indirectly through PPU registers.
2. The latch, buffer, and delays of `$2005/$2006/$2007` are central to PPU emulation difficulty.
3. AprNes places PPU register behaviour inside a dot-level pipeline, not as ordinary variable updates.
