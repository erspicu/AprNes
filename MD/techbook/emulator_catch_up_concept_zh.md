# 模擬器中的 Catch-Up 是什麼，為什麼越高階的 Timing 策略越難設計

## 前言

在討論模擬器 timing 時，大家很容易把注意力放在：

- `per-frame`
- `per-scanline`
- `per-dot`
- `per-cycle`
- `master clock`

但實際做模擬器時，真正很常讓架構變複雜的，不只是 timing 粒度本身，而是另一個常被低估的觀念：

**catch-up**

簡單說，`catch-up` 就是：

> 某個元件先往前跑了，而另一個元件暫時還沒跟上；等到需要互動、觀察、同步或產生副作用時，再把落後的元件補跑到對的時間點。

這個觀念幾乎存在於所有非「全元件同時逐 tick 前進」的模擬器裡。  
而且越往高精度、高複雜度的 timing 策略走，`catch-up` 的設計空間通常越小，錯的代價越高，最後真正考驗的就是開發者對**時間模型設計**的能力。

這篇文章想同時讓兩種讀者都能讀懂：

- 對資訊技術有興趣、但不一定做過模擬器的人
- 真正打算設計 emulator core 的開發者

## 先用直覺理解 Catch-Up

你可以把模擬器想像成一個有很多角色的舞台：

- CPU 在做指令
- PPU 在畫畫面
- APU 在產生聲音
- mapper 在看位址線、計數 IRQ 或切 bank

如果所有角色都每一拍一起前進，事情最單純，但也最貴。  
很多模擬器不這樣做，而是採取比較便宜的方式：

- 先讓 CPU 跑一段
- 等 CPU 要讀寫 PPU、查 IRQ、或要提交一幀畫面時
- 再把 PPU / APU / mapper 補跑到同樣的邏輯時間

這個「補跑」動作，就是 `catch-up`。

所以 `catch-up` 的本質不是某個特定演算法，而是一種同步策略：

- 平常先容忍不同元件的模擬進度不完全一致
- 在關鍵觀察點把它們對齊

## 為什麼要用 Catch-Up

最直接的原因是：**省成本**。

如果你每個最小時間單位都同時推進所有元件：

- 實作會比較直接
- 觀念上比較接近真硬體
- 但運算量通常很大

如果你允許某些元件延後更新，再在需要時補上，你就能得到：

- 較少的函式呼叫
- 較少的狀態切換
- 較大的批次更新空間
- 較好的效能

這也是為什麼很多模擬器，即使不是刻意追求粗糙 timing，也仍然會有某種形式的 `catch-up`。

## 一個非常簡單的例子

假設你在做一個很粗略的 NES emulator，並決定：

- CPU 是主時鐘
- 每執行完一條 CPU 指令
- 再讓 PPU 一次補足相對應的進度

那你的模型可能像這樣：

1. CPU 執行一條指令
2. 算出這條指令花了幾個 cycle
3. PPU 一次補跑對應的週期數
4. APU 也補跑對應的週期數
5. 再看有沒有 IRQ、NMI、畫面更新等事件

這就是最典型的 `catch-up` 架構之一。

它的優點是：

- 好理解
- 好做
- 很多遊戲已經能跑

它的限制是：

- 如果某些副作用其實發生在指令中途，你可能太晚才看見
- 如果某些 PPU / mapper 事件需要更精確的時間點，你的模型會開始出現誤差

## Catch-Up 並不只是「補時間」，而是「補可觀察狀態」

這點很重要。

很多人第一次想到 `catch-up`，會以為只是：

- 補一些 cycle
- 把 counter 加上去

但真正困難的地方是，模擬器不是只在算時間，而是在維護**可觀察行為**。

當你讓某個元件晚一點再追上，真正要問的是：

- 它的內部狀態有沒有在補跑時正確重建
- 在這段延遲期間，本來應該被其他元件看見的事件，有沒有遺漏
- 補跑之後，外界看到的結果，是否仍和真實時間順序一致

也就是說，`catch-up` 不只是時間對齊，還是：

- 事件對齊
- side effect 對齊
- bus / register 可見性對齊

## 在粗模型裡，Catch-Up 通常比較容易

如果你的 timing 模型很粗，例如：

- `per-frame`
- 很粗的 `per-scanline`
- instruction-level CPU 主導模型

那 `catch-up` 的設計空間通常比較大。

原因是：

- 模型本來就容忍近似
- 很多中間狀態本來就不打算保留
- 外部只觀察較大粒度的結果

在這種情況下，你可以比較自由地做：

- 批次推進
- 延後計算
- 合併事件
- 在邊界時一次性修正狀態

這也是為什麼比較粗的模擬器，常常比較容易做出「速度很高」的版本。

## 但模型越粗，並不代表事情一定簡單

這裡有一個常見誤解。

很多人會想：

> 既然粗模型自由度比較大，那 catch-up 不就比較簡單嗎？

不完全對。

比較準確地說是：

- **你有比較大的操作空間**
- 但你同時也要更小心地決定哪些資訊可以被壓掉，哪些不行

也就是說，粗模型的困難點是：

- 不是每件事都精確做
- 但你得知道不精確做會壞在哪裡

這種困難，比較像工程判斷問題。

## 模型越細，Catch-Up 的「空間」反而越小

當你開始往更高精度的 timing 模型移動，例如：

- 更細的 `per-scanline + intra-line event`
- `per-dot`
- `per-cycle`
- `master clock`

事情會發生一個很重要的變化：

**你能自由延後、合併、壓縮、偷懶的空間會快速縮小。**

原因很簡單：

- 更多中間狀態開始有意義
- 更多邊界時間點開始可觀察
- 更多副作用不再能事後補帳

在這種模型裡，`catch-up` 不是不能做，而是：

- 可用的窗口更短
- 可延遲的內容更少
- 同步點更嚴格
- 一旦跨錯邊界，錯誤會立刻傳播

所以高精度模型中的 `catch-up`，常常不像「自由補跑」，而比較像：

- 非常嚴格的 deferred execution
- 非常嚴格的 timestamp alignment
- 非常小心的 side effect 排程

## 為什麼越複雜的策略，Catch-Up 越難設計

這是整篇最核心的重點。

當你的模擬策略越複雜，困難不只在元件變多，而是：

- 元件之間的互相觀察變多
- 可觀察時間點變多
- 中間狀態變多
- 事件順序的約束變多

舉例來說，在一個簡單 CPU 主導模型中，你可能只要處理：

- CPU 先跑
- PPU 補進度
- 最後檢查事件

但在更高精度模型裡，你可能要考慮：

- 某個 register write 不是立刻生效，而是延遲幾個 phase
- 某個 IRQ 不是在 line 結尾，而是在某個邊界轉換時被觀察
- 某個 open bus / latch 狀態在補跑期間不能被覆蓋
- 某個 mapper 需要看到特定線路的上升沿或下降沿
- 某個 sprite / background 條件必須在極小窗口內決定

到這裡，`catch-up` 就不再只是「把數字補上」，而是變成：

> 我能不能在允許延後更新的前提下，仍然完整保留這個模型對事件順序的所有承諾？

這個問題，本質上已經是模型設計能力的考驗。

## 一個很重要的觀念：Catch-Up 其實是在消費「設計餘裕」

如果把 timing 模型想成一種合約，那 `catch-up` 就是在問：

> 這份合約允許我延後多久才補交結果？

在粗模型裡，這份合約通常比較寬鬆。  
你可以晚一點再交，因為很多中間過程本來就不被觀察。

但模型越細，合約越嚴格。  
你每延後一步，可能就已經跨過一個可觀察邊界。

所以可以說：

- 粗模型有比較大的設計餘裕
- 細模型有比較小的設計餘裕

而 `catch-up` 本質上就是在消費這個餘裕。

這也是為什麼越高擬真的模擬器，`catch-up` 常常越難優雅地做。

## 實務上常見的 Catch-Up 類型

雖然不同模擬器做法差很多，但大方向上，常見的 `catch-up` 可以分成幾類。

### 1. 時間量補跑

最單純的形式：

- 補 cycle
- 補 dot
- 補 scanline

這種通常出現在較粗或中等精度模型。

### 2. 事件驅動補跑

不是每一步都補，而是：

- 跑到下一個重要事件
- 或在互動前補到事件邊界

這種做法通常比純時間量補跑更有效率，也更考驗事件模型。

### 3. 延遲提交狀態

例如某些寫入先記成 pending：

- 真正效果延後到某個固定 timing point 才生效
- 生效前，讀路徑仍看到舊值

這也是一種 `catch-up`，只是補的是「狀態提交」而不是純時間。

### 4. 局部元件 catch-up

不是所有元件一起追，而是：

- 只有 PPU 補
- 只有 mapper 補
- 只有音訊管線補

這在大系統裡很常見，但也最容易出現「某個子系統追上了，另一個還沒追上」的微妙 bug。

## 對一般技術讀者的直覺比喻

如果你不是 emulator developer，可以把 `catch-up` 想像成一種「延後結帳」。

平常系統先記帳，不立刻結清。  
等到你真的要看結果、要互動、要查帳的時候，再一次把欠的部分補齊。

這種方式的好處是快。  
壞處是：

- 帳不能算錯
- 順序不能亂
- 不能漏掉中間本來應該被看到的事情

而模擬器的難處在於，它不是只有錢有沒有對，還包括：

- 誰先看到
- 什麼時候看到
- 看到的是新值還是舊值
- 某個副作用是否已經發生

## 對真正開發模擬器的人來說，該怎麼思考 Catch-Up

如果你是要設計 emulator core 的人，我會建議你先問自己幾個問題。

### 1. 誰是時間主體

你要先決定：

- CPU 是主體
- PPU 是主體
- 還是整機用 master clock

這會直接決定 `catch-up` 的方向，因為其他元件通常都是對主體追進度。

### 2. 哪些邊界是不可跨越的

每個模型都有一些不能隨便跨的時間邊界，例如：

- register side effect 生效點
- IRQ 可被觀察的時間點
- A12 edge
- line / frame 轉換
- 某些 latch / buffer 更新點

只要一個 `catch-up` 機制可能越過這些邊界卻沒有正確拆帳，它就不安全。

### 3. 哪些狀態可以延後，哪些不能

你需要明確區分：

- 可延後推進的 state
- 可延後提交但不可延後觀察的 state
- 完全不能延後的 state

這個分類如果不清楚，後面一定會一直修 timing bug。

### 4. Catch-Up 是全域機制，還是局部機制

有些系統把 `catch-up` 做成統一的全域規則。  
有些系統則每個子系統自己定義。

前者的好處是：

- 一致
- 比較容易 reasoning

缺點是：

- 可能犧牲一些效能
- 會限制局部最佳化

後者的好處是：

- 彈性高
- 局部效能可能更好

缺點是：

- 很容易出現子系統之間的同步縫隙

### 5. 未來優化空間在哪裡

有些 `catch-up` 設計雖然正確，但之後很難優化。  
有些則一開始就保留了：

- 批次處理空間
- event table
- deferred queue
- 專用 hot path

如果你知道未來會追效能，這些在一開始就值得想。

## 一個殘酷但真實的結論

很多人以為模擬器越高精度，越接近「照著硬體做」，就越不需要架構技巧。  
其實不是。

高精度模型雖然理論上更接近真實硬體，但工程上你仍然必須面對：

- 怎麼切 phase
- 怎麼做 deferred state
- 怎麼安排 event 順序
- 哪些地方可以 batch
- 哪些地方一定要同步

也就是說，越高階的策略，不只是更花算力，還意味著：

- `catch-up` 的自由度更低
- 錯誤容忍空間更小
- 對模型邏輯自洽性的要求更高

最後考驗的已經不是「有沒有把硬體名詞背熟」，而是：

**你能不能設計出一個既正確、又能運作、還能被優化的時間模型。**

## 結語

`catch-up` 不是模擬器裡的邊角技巧，它其實是 timing 架構裡非常核心的一部分。

在粗模型中，它代表：

- 效能空間
- 近似空間
- 架構彈性

在細模型中，它代表：

- 同步壓力
- 邊界控制
- 事件承諾

所以一個模擬器的成熟度，常常不只看它 timing 粒度多細，還要看它的 `catch-up` 設計是否清楚：

- 什麼時候允許延後
- 延後後怎麼補
- 補的時候怎麼維持可觀察順序
- 哪些地方絕對不能模糊

如果說 timing 模型決定了你「模擬世界的解析度」，那 `catch-up` 設計決定的就是：

**在這個解析度下，你能不能讓整個世界仍然合理地一起運作。**
