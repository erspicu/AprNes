# 為什麼「高品質 Per-Scanline NES Emulator」其實很難

## 前言

很多人第一次接觸模擬器時，會很自然地以為：

- 最簡單的是 `per-frame`
- 再來是 `per-scanline`
- 最後才是 `per-dot`、`per-cycle`、`master clock`

這個排序沒有錯，但它很容易讓人產生一個誤解：  
`per-scanline` 只是比較粗、比較不準、也比較容易做。

實際上，**如果目標不是教學用原型，而是要在 `per-scanline` 這種限制下，仍然高效率地跑動多數商業遊戲，那它本身就是一種很硬的工程挑戰。**

難的地方不在於「完全模擬硬體」，而在於：

- 你明知模型不夠細
- 但你還是要讓它表現得像足夠細
- 而且不能把系統塞滿無法維護的特判

這篇文章要談的，就是這條路線真正難在哪裡、值不值得做、適合什麼樣的開發者，以及做這條路線時應該怎麼思考。

## 什麼是 Per-Scanline Timing

NES 的 PPU 每一幀會跑很多條 scanline，每條 scanline 又包含大量 dot。  
如果用最細的方式處理，你會逐 dot、逐 cycle 甚至逐 master clock 去推進 CPU、PPU、APU、mapper 與 bus side effect。

`per-scanline` 的做法則是：

- 以一整條 scanline 當成主要更新單位
- 每跑完一條 line，再處理畫面、IRQ、scroll、sprite、音訊或其他事件
- 某些特別重要的時序點，才額外補上局部 event 或特殊處理

它的核心思想不是「精確重建每個硬體瞬間」，而是：

**用比較粗的時間模型，換取更高效能與更低複雜度，再用少量高價值補丁，補回相容性。**

## 為什麼這條路線看起來簡單，實際上不簡單

### 1. NES 不是只要每條線更新一次就能交代

NES 有很多行為不是「scanline 結束後再算」就可以。

例如：

- `sprite 0 hit`
- MMC3 一類依賴 PPU A12 邊界的 IRQ
- mid-frame scroll split
- PPU register write 的時序副作用
- DMC / APU 與 CPU steal / side effect

這些現象常常不是「第幾條線發生」，而是「某條線內的哪一段發生」。  
也就是說，**scanline 本身太粗了。**

因此你一開始選擇 `per-scanline`，就等於接受了一件事：

> 你的主模型天生不夠表達硬體真相。

接下來的挑戰，就是怎麼在不升級成完整 `per-dot` 架構的前提下，把必要資訊補回來。

### 2. 真正困難的是判斷「哪些一定要補」

`per-scanline` 最大的工程難點，不是補丁寫不出來，而是：

- 哪些硬體現象真的重要
- 哪些只影響少數 ROM
- 哪些可以粗略近似
- 哪些一旦近似就會讓一整類遊戲壞掉

這是一種「架構層級的取捨能力」。

如果判斷錯誤，結果通常有兩種：

- 你補太少，遊戲相容性很差
- 你補太多，系統變成隱形的 `per-dot` 模型，卻還保留 `per-scanline` 架構的混亂成本

### 3. 很容易從整潔架構，退化成補丁森林

許多 `per-scanline` 模擬器最後真正的問題，不是精度不夠，而是可維護性崩掉。

常見退化方式：

- 某款遊戲有問題，就加一個 mapper hack
- 某個 split timing 不對，就加一個 line-local 特判
- 某個 IRQ 差一點，就再加一個 event 偏移量
- 某個 status flag 不準，就在 render 前後補一次修正

如果沒有一開始就設計好「例外機制」與「時序補丁層」，最後系統會變成：

- 表面上是 `per-scanline`
- 實際上是由大量局部修補撐住
- 任何新 bug 都可能牽動舊 hack

這是這條路線最真實的風險。

## 為什麼它仍然值得做

即使如此，`per-scanline` 仍然非常有價值。

因為它追求的不是「最高擬真」，而是另一種同樣困難的目標：

- 很高的執行效率
- 很好的實用相容性
- 較低的整體運算成本
- 比完整微時序模型更容易落地到弱硬體或多平台

這不是退而求其次，而是不同方向的工程最佳化。

如果 `master clock` 路線是在問：

> 我能不能把真實硬體重建得足夠接近？

那高品質 `per-scanline` 路線是在問：

> 我能不能在一個先天不足的模型下，仍然用最小代價做出大部分玩家可接受的結果？

這個問題一樣很難，而且非常實用。

## 這條路線真正的核心能力

如果你想做一個好的 `per-scanline` NES emulator，真正要培養的能力大概有五種。

### 1. 分層思考能力

你不能把所有 timing 問題都塞進同一層。

比較健康的分法通常是：

- 主模型：scanline 驅動
- 關鍵事件層：line 內 event、IRQ、split 點
- 特定元件層：mapper、PPU status、sprite hit、DMC 等局部補強
- ROM 特例層：只有明確證據時才放進來

如果沒有這種分層，系統很快就會糊成一團。

### 2. 找「最小必要精度」的能力

不是所有硬體細節都值得在 `per-scanline` 模型裡重建。

真正重要的是：

- 哪些資訊缺了會直接讓大類遊戲壞掉
- 哪些資訊只在少數測試 ROM 才會暴露
- 哪些現象可用近似值替代

例如對很多實用導向專案來說，重點通常不是完整複製每個 PPU dot，而是優先掌握：

- scanline 邊界上的狀態轉移
- 會影響 IRQ 的可觀察事件
- 會影響 split 或 sprite 判定的幾個關鍵時刻

### 3. 控制補丁擴散的能力

你應該假設：

> `per-scanline` 一定需要 patch，但 patch 必須被制度化。

所謂制度化，意思是：

- 補丁要有固定入口
- 補丁要有命名與責任邊界
- 補丁要能被測試與關閉
- 補丁要知道自己在修什麼，不是神秘常數

這對長期維護極重要。

### 4. 測試與回歸驗證能力

`per-scanline` 的可怕之處在於，很多 bug 不會立刻炸掉，而是：

- 某款遊戲的標題畫面正常
- 進入遊戲後 split 不對
- 或某關卡偶爾閃爍
- 或特定 mapper 的 IRQ 節奏慢慢漂掉

所以這種架構非常依賴：

- 測試 ROM
- 真實商業遊戲回歸
- 問題分類紀錄
- 修補前後的行為比對

沒有這些，你很容易以為自己「修好了」，其實只是把問題移到別處。

### 5. 接受「不是所有遊戲都值得為它破壞架構」的能力

這一點很重要。

如果你的目標本來就是：

- 高效率
- 跑大多數商業遊戲
- 維持合理可維護性

那你就必須接受：

- 有些極端 timing case 可能不支援
- 有些 ROM 不值得為了它把整個架構變醜

這不是偷懶，而是產品與架構目標的一部分。

## 最容易踩到的三種陷阱

### 陷阱 1：以為只要「每條線算一次」就夠了

這通常只夠做到：

- 畫面大致有出來
- 部分簡單遊戲可動

但一旦碰到需要更細時間資訊的遊戲，很快就會出現：

- split 錯位
- IRQ 失準
- sprite hit 時機不對
- 特定特效失效

### 陷阱 2：不願意補 event，導致整體精度卡死

有些開發者會想維持「純 scanline 模型」的美感，結果不願意承認 line 內事件是必要的。  
這通常會讓相容性停在一個上不去的位置。

比較成熟的做法是：

- 主體仍是 `per-scanline`
- 但允許少量、明確、可驗證的 mid-line event

這種折衷通常比硬撐純 line 模型更實際。

### 陷阱 3：event 加太多，最後自己變成壞掉的 per-dot

另一個極端是反過來：

- 這裡補一個 event
- 那裡補一個 pseudo-dot
- 某個 mapper 再補半條線

最後得到的是：

- 比 `per-dot` 還難懂
- 比 `per-dot` 還不系統化
- 卻沒有 `per-dot` 那種結構完整性

這種情況很常見，也很危險。

## 一個比較健康的開發策略

如果你真的想走這條路，我比較建議這樣規劃。

### 第 1 階段：先做出穩定、乾淨的 scanline 核心

目標不是一次就跑全世界，而是先讓模型本身有清楚責任。

這個階段重點：

- CPU/PPU/APU/mapper 的主驅動關係清楚
- frame / scanline 邊界行為一致
- 基本 rendering 與基本 mapper 可以穩定運作

### 第 2 階段：只補高價值 timing 事件

開始補那些對大量遊戲真的重要的現象，例如：

- 常見 mapper IRQ 需求
- 常見 split scrolling 需求
- `sprite 0 hit` 類型的必要邊界

這裡的原則是：

> 每補一個事件，都要知道它解決的是哪一類相容性問題。

### 第 3 階段：建立例外管理制度

當 patch 開始增長時，必須把它們制度化。

例如：

- 以事件類型分類
- 以 mapper 類型分類
- 以是否影響全域 timing 分類

這能避免系統日後變成 bug-hack 垃圾場。

### 第 4 階段：用 profile 決定是否值得再細化

這階段不是先追更細 timing，而是先問：

- 效能瓶頸在哪裡
- 不相容主要集中在哪類行為
- 哪些問題真的值得升級模型

有時候你會發現：

- 瓶頸根本不在 timing 粒度
- 問題其實出在 mapper 行為
- 或畫面管線比 timing 更值得優化

## 對不同開發者的建議

### 如果你是一般資訊愛好者

你可以把 `per-scanline` 理解成一種很聰明的近似法。

它不是完整模仿每個電路瞬間，而是：

- 先抓住大時間尺度
- 再針對重要細節補洞

它的工程美感在於：  
不是最真，但追求很高的實用價值。

### 如果你是剛開始寫模擬器的人

`per-scanline` 是一條可以學到很多東西的路，但不要把它誤認成「省事路線」。

你應該先想清楚：

- 你是想做教學專案
- 還是想做能跑很多商業遊戲的實用模擬器

前者可以簡單很多，後者則一定會碰到 timing 補丁設計問題。

### 如果你是認真做 emulator core 的開發者

你最需要問自己的，不是「能不能做」，而是：

- 產品目標是什麼
- 相容性目標是什麼
- 維護人力有多少
- 未來是否要升級到更細粒度模型

如果未來很可能走向 `per-dot` 或更細時序，那現在的 `per-scanline` 架構就應該為升級預留空間。  
如果你就是要長期維持高效率實用派，那就應該把「補丁制度化」當成一級設計目標。

## 它和高擬真路線的本質差異

高擬真路線，例如 `per-dot`、`per-cycle`、`master clock`，追求的是：

- 對真實硬體時間結構的高還原
- 讓副作用自然從模型中長出來

而高品質 `per-scanline` 路線追求的是：

- 在不完整的模型上，精準重建可觀察結果

前者比較像：

> 我把世界做得夠真，所以很多現象自然會對。

後者比較像：

> 我知道模型不夠真，所以我要很聰明地選擇哪些地方要補真。

兩者都困難，只是困難的性質不同。

## 結語

`per-scanline` 不是落後技術，也不是只適合新手的簡化版。  
如果你的目標是：

- 高效率
- 多數商業遊戲可玩
- 合理的工程成本

那它完全可以是一條嚴肅、實用、而且很有技術含量的開發路線。

但這條路線真正難的地方，不在模擬得不夠細，而在於：

- 明知不夠細，還要知道哪裡必須補
- 補了之後，還不能失去整體架構控制
- 追求相容性的同時，還要維持速度與可維護性

所以從工程角度來看，**高品質 `per-scanline` NES emulator 不是「比較簡單的選擇」，而是「另一種非常難的選擇」。**
